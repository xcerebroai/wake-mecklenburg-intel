## Answers to the flagged open classification questions

**(a) Does code enforcement have a weight in the standard schema?**
**Resolved — yes, and this is no longer an open question.** `CODE_VIOLATION_NOTICE`, `DEMOLITION_ORDER`, and `CONDEMNATION_NOTICE` all have real `BASE_SCORE` entries in `scaffold/pipeline/score.py` (25, 50, 45 respectively) and are marked `lead_generating`/`P0` in `canonical_doc_types.json`. No operator call needed on *whether* code enforcement scores — the only remaining work is mapping Charlotte's `CaseType` field values to the correct one of these three subtypes.

**(b) Taxdel ↔ foreclosure overlap — propose a stacking rule.**
**Partially resolved, partially still needs your design call.** The risk is smaller than it looked: since `delinquent_tax` has no canonical doc type or base score of its own (it's enrichment, per the correction above), it structurally cannot double-sum against a foreclosure signal's base score — `score.py`'s mechanism takes the `max()` single strongest signal, not a sum across signal types, so this specific pairing is safe by construction, not by an explicit named rule. What genuinely has **no predefined rule anywhere in the framework** (confirmed by direct repo research — checked `18_signal_aggregation_contract.md` and `19_aggregator_idempotency_rule.md`) is the general "boost, don't double-count" pattern for cases where two *scored* signals legitimately co-occur (e.g. `sp_foreclosure` + `in_rem_tax_fc` on the same Mecklenburg parcel, both real doc types with real base scores). That case does need your design call — the stack-depth bonus (`STACK_BONUS = {2: +12, 3: +24}`) already provides some signal for "multiple things are happening," but there's no rule preventing, say, two foreclosure-bucket signals from both being counted toward stack depth as if they were independent categories when they're really the same underlying event described twice.

**(c) Confirm all three foreclosure types merge at the scoring bucket while staying distinct upstream.**
**Confirmed, this works as you'd expect.** Per `18_signal_aggregation_contract.md` §18.B, the aggregation key is `(parcel_id, canonical_doc_type, signal_type)` — `canonical_doc_type` stays granular there, so `sp_foreclosure`/`judicial_tax_fc`/`in_rem_tax_fc` remain three distinct types for aggregation and dedup purposes. They'd only merge at the `lead_pattern: "foreclosure"` level, which is what `score.py`'s `BASE_SCORE` lookup and the stack-depth counting key off of. So: distinct upstream, merged only at the scoring-bucket layer — exactly the intent, now confirmed against the real aggregation contract rather than assumed.

**(d) County scope — must any single-county doc_type be explicitly scoped?**
**Confirmed, and already reflected in the config.** `in_rem_tax_fc` is Mecklenburg-only (no equivalent found in Wake recon so far) and is marked as such in `config/counties/mecklenburg_nc.json`'s `sources` block — it simply doesn't appear in `wake_nc.json` at all, which is how the framework's per-county config design naturally enforces this (there's no shared/multi-county config file to accidentally leak a Meck-only doc type into Wake's classify stage).

## New canonical types this build likely needs to propose upstream

Four NC-specific doc types have no existing equivalent in `canonical_doc_types.json`, which is currently shaped around Texas non-judicial-foreclosure and heirship-affidavit practice:

- `ESTATE_CASE_OPENED` (or similar) — NC E-case estate administration filing
- `SP_FORECLOSURE_NOTICE_OF_HEARING` (or similar) — NC SP power-of-sale foreclosure
- `JUDICIAL_TAX_FORECLOSURE_COMPLAINT` (or similar) — NC GS 105-374 mortgage-style tax foreclosure
- `IN_REM_TAX_FORECLOSURE_JUDGMENT` (or similar) — NC GS 105-375 in-rem tax foreclosure (Mecklenburg-scoped)

Adding these is a change to the shared framework repo (`canonical_doc_types.json`), not just this county's config — worth flagging as a decision with broader scope than a single build, since other future non-TX counties would benefit from the same additions.
